THE ONNX OPERATOR ORACLE FIXTURES
=================================
One tiny ONNX graph per operator - and per awkward variant of it - with a set of
inputs and the outputs ONNX Runtime produced from them, checked in so that the
managed interpreter can be held to somebody else's arithmetic with nothing
installed.

WHAT IS HERE
    <case>/model.onnx   the graph, one or a few nodes
    <case>/case.json    what the inputs and outputs are called, their element
                        types and shapes, which file holds each one, and - for
                        the one case that needs it - how far its numbers may be
                        from ONNX Runtime's
    <case>/in_*.bin     the inputs, raw little-endian elements, row-major
    <case>/out_*.bin    what ONNX Runtime computed from them, the same way
    cases.json          every case name, and the graphs that must be REFUSED
    Refusals/*.onnx     graphs the engine is required to turn away when it
                        loads them: an operator it does not implement, an
                        operator set too old for the meanings it implements, an
                        element type it does not compute in, an attribute it
                        would otherwise ignore, a node reading something nothing
                        produces, a file cut in half

WHO OWNS THEM
    They are OURS. Every file here was generated by generate_fixtures.py in this
    same folder, from numbers that script makes up with a seeded random number
    generator - no publisher's model, no third-party data and no downloaded file
    is among them. They carry this repository's licence (MIT); see LICENSE at
    the root.

HOW THEY WERE MADE
    generate_fixtures.py, run BY HAND, once, in a virtual environment holding
    onnx and onnxruntime:

        <venv>/bin/python generate_fixtures.py

    It builds each graph twice - the first time with its outputs left untyped so
    that ONNX Runtime settles what they are, the second time with the type and
    shape ONNX Runtime produced - runs the inputs through ONNX Runtime, and
    writes everything above. The seed is fixed, so running it again reproduces
    the same numbers.

    A graph that uses a CONTRIBUTED operator - one a runtime vendor added, which
    the ONNX package has no schema for - is declared against a newer operator
    set and a newer file format and is NOT put through the ONNX checker or its
    strict shape inference. ONNX Runtime is what says such a graph is valid, and
    it says so by running it.

    THE TEST SUITE NEVER RUNS IT. The tests read the files as they are checked
    in, which is the whole point: what they compare against was computed by
    another implementation of the specification, not by ours. Running the suite
    needs no Python, no network and nothing outside this repository.

    Regenerating is a deliberate act. Every output file changes when the script
    changes, so a change here should be one somebody meant to make.

WHY THEY ARE SMALL
    Every tensor is a handful of elements and every graph is a handful of nodes.
    What is being tested is the MEANING of an operator - which axis, which
    broadcast, which rounding, what an empty tensor does - and none of that needs
    a large tensor. Speed is measured elsewhere, on real models, behind the
    environment gates.
