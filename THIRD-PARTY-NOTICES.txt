THIRD-PARTY SOFTWARE NOTICES AND INFORMATION

CodeBrix.Ollama is a pair of .NET libraries for downloading, managing and
running large language models in-process: CodeBrix.Ollama.ModelManager (a model
store and registry client) and CodeBrix.Ollama.ModelRunner (a managed binding
over a self-built native inference library, with its own chat-template,
tool-call and grammar machinery). As of 2026-09-16 both libraries are written,
and the repository holds the native build tooling and a native library for all
seven runtime identifiers. ModelManager is a partial port of the Ollama
server's Go code (entry 3). ModelRunner transcribes llama.cpp's public C
headers and ports four further bodies of code: llama.cpp's JSON-schema-to-
grammar converter (entry 1), Ollama's template, thinking and tools packages
(entry 3), the Go standard library's text/template and the helpers it needs
(entry 5), and one small Go module (entry 6). LLamaSharp (entry 4) and the
Jinja project (entry 7) were read but never copied; both are listed anyway, so
that the record is complete rather than merely obligatory. Entries 8 to 14
cover the public models' chat templates the ModelRunner test suite carries as
fixtures. Entry 15 covers ONNX Runtime's quantization tools, whose Python and
C++ code ModelManager's managed reduction engine ports so that reducing a model
needs none of them installed. Entry 16 covers the SkyTNT MIDI model's own
generation loop and MIDI tokenizer, which ModelRunner's MIDI driver ports so
that generating music needs nothing installed either - and records what was
deliberately NOT taken from the MIDI file library that repository vendors.
Entry 17 covers the GPT-2 byte-level tokenizer as Hugging Face's transformers
library writes it, which ModelRunner's managed tokenizer ports so that
generating TEXT from an ONNX bundle needs nothing installed either. Entry 1 covers a second port in the same library:
llama.cpp's own checkpoint converter, which is Python, ported so that turning a
checkpoint into a GGUF file needs nothing installed either.

Four distinct things in this repository come from other people today, and all
four are covered below. They are a way of grouping what is here, not the list
of entries: the numbered entries further down are organised by copyright
holder, and one of these four things can span several of them.

  1. THE VENDORED SOURCE. llama-native-tools/llama.cpp/ is an unmodified
     snapshot of the build-sufficient subset of the upstream llama.cpp source
     tree (which contains the ggml tensor library), committed to this
     repository so the native libraries can be rebuilt from it alone, years
     from now, with no dependency that may have disappeared. It is the only
     source the native libraries are ever built from.

  2. THE SHIPPED BINARIES. The package's runtimes/<rid>/native/ folders under
     src/CodeBrix.Ollama.ModelRunner/ contain libcodebrix_llama.dylib /
     libcodebrix_llama.so / codebrix_llama.dll compiled from exactly that
     source, one per runtime identifier - all seven of them as of 2026-09-16:
     linux-arm64, linux-riscv64, linux-x64, osx-arm64, osx-x64, win-arm64 and
     win-x64.

  3. THE PORTED MANAGED CODE. src/CodeBrix.Ollama.ModelManager/ contains C#
     code ported by hand from the Ollama server's Go source: model-name
     parsing, the GGUF metadata reader, the Modelfile parser, the registry
     protocol and blob downloader, and the manifest/blob store layout.
     src/CodeBrix.Ollama.ModelRunner/ contains C# transcribed from llama.cpp's
     public C headers (Native/) and ported from llama.cpp's schema-to-grammar
     converter (Grammar/), from the Go standard library's text/template
     (Templates/OllamaGo/), and from Ollama's template, thinking and tools
     packages (Templates/OllamaGo/ and Parsing/).
     src/CodeBrix.Ollama.ModelManager/Onnx/Quantization/ contains C# ported
     from ONNX Runtime's own quantization tools, in Python and in C++ (entry
     15), src/CodeBrix.Ollama.ModelRunner/Drivers/SkyTnt/ contains C# ported

MODIFICATIONS MADE DURING THE MANAGED PORT
    - The C# drops C++ idioms and nullable annotations for this repository's
      conventions, and C++ error returns and negative status codes became this
      library's exception types (ModelRunnerException and its subclasses).
    - The 36 functions llama.h marks DEPRECATED are deliberately not bound,
      and llama_opt_params' optimizer-parameter callback is bound as an opaque
      pointer because ggml-opt.h itself is not bound.
    - The converter refuses a remote $ref - one pointing at another document
      over http - rather than fetching it, because converting a schema does no
      I/O; it guards every JSON value kind and raises GrammarException instead
      of widening a schema silently; it reports what it could not express as
      warnings a caller can ask for; and const and enum numbers keep the
      schema's own spelling.
    - EngineSamplerChain deviates from common/sampling.cpp twice, on purpose:
      the penalty samplers run over the full vocabulary before truncation, as
      llama.h's own comment advises, and only generated tokens are fed to
      them, so penalties see less history than llama.cpp's main program gives
      them.
    - The conversion port reads FILES where the Python reads a loaded
      transformers model. It therefore fills in for itself the two model-class
      defaults the Python gets for free (the head width and the key-value head
      count), reads a model card's front matter with a reader of its own rather
      than a YAML library, and takes the model identifier the general metadata
      is derived from as a parameter instead of using the directory name
      implicitly. It covers the llama architecture, the GPT-2 byte-level BPE
      tokenizer and the SentencePiece tokenizer, and refuses anything else by
      name rather than converting it approximately. What it does convert it
      converts to the byte: the checked-in fixtures are compared with the
      Python's own output over the whole file.
    - Two rules of the Python's LlamaModel.set_vocab are deliberately NOT
      ported, and a checkpoint that meets either converts to a correct file
      that is not byte-identical to the Python's: a vocabulary of exactly
      32,016 tokens is given four fixed infilling token identifiers, and one of
      exactly 49,152 tokens is given a false add_bos_token. Both write keys
      whose position among the others decides the file's bytes, and the only
      checkpoints that would show that position are model families far too
      large to check in as a test fixture, so the rules are recorded rather
      than guessed at.
    - Where a SHARDED checkpoint's index and its files disagree, the port
      refuses by name in two places the Python does not: a tensor held by two
      parts (the Python silently keeps the copy from the later part) and a
      weight map that lists one tensor twice (Python's JSON reader silently
      keeps the last entry). The cases the Python does refuse - a tensor in a
      part that the index does not list, and a tensor the index lists that no
      part holds - are refused here too.
    - A SentencePiece model's own USER_DEFINED pieces are written as ORDINARY
      tokens, which is what the Python does: only an added_tokens.json entry or
      an added-token table entry makes a token user-defined in the output.
    - Where the Python calls the SentencePiece LIBRARY to open a tokenizer.model,
      the port reads the file itself. A tokenizer.model is a Protocol Buffers
      message (SentencePiece's ModelProto), and three of its fields - a piece's
      text, its score and its kind - are all a conversion needs, so they are
      read with the Protocol Buffers codec this library already carries for ONNX
      and everything else in the file is skipped. NO CODE IS TAKEN FROM the
      SentencePiece project, nothing depends on it at run time, and no file of
      it is shipped: only the published wire layout of that message is relied
      on, in the same way a reader of any documented file format relies on its
      layout. The values the port then derives from those fields - which piece
      kind becomes which GGUF token type - are the Python's, above.

MODIFICATIONS MADE DURING THE ModelManager PORT
    - Go's package-level functions and global state became instance methods
      on ModelStore / RegistryClient with explicit ModelStoreOptions; the
      store directory is a parameter, not an environment lookup (the
      OLLAMA_MODELS default is preserved as the default value only).
    - Resumable downloads keep ONE JSON sidecar per blob
      (<blob>.codebrix-parts.json) and one data file (<blob>.codebrix-partial)
      instead of Ollama's "-partial" and "-partial-<n>" files, so this
      library's in-progress files never collide with a co-located Ollama
      server's. Consequently Ollama's own partial files are never read, and
      PruneLayers' deletion of unrecognised files in blobs/ was narrowed to
      this library's own sidecar names.
    - The process-wide download de-duplication (blobDownloadManager, the
      acquire/release reference counting) and the sparse-file hint were not
      ported; one call downloads one blob.
    - Registry authentication: only the bearer-token retry after a 401
      challenge is ported. Ollama's ed25519 key signing (auth.go) is not.
    - Manifests and blobs are written to a temporary file and renamed into
      place; Ollama writes in place.
    - GGUF reading is a single eager forward pass producing an immutable
      snapshot; the lazy iterator machinery (lazy.go), the tensor-data
      section reader and the multi-shard Model aggregation (model.go) were not
      ported. Reflection-based value conversion (keyvalue.go) became explicit
      type switches. Ollama's unexported tensor-type identifiers are exposed.
    - Modelfile parsing: file hashing, glob expansion, "~" expansion and
      safetensors/PyTorch directory detection (parser.go CreateRequest) were
      not ported; typed parameter values use int32 where Go uses int64.
    - Create: safetensors import, create-time quantization, DRAFT models,
      split-GGUF grouping, Ollama's built-in template auto-detection
      (template.Named) and its Go-template validation were not ported; the
      template text is stored as written. LoRA ADAPTER files ARE accepted
      (older Ollama behaviour), whereas the upstream commit rejects them.
    - Capability inference keeps the GGUF- and template-text-based rules and
      drops the renderer/parser/model-family special cases and the Go-template
      syntax-tree walk for thinking tags.
    - Push (upload.go), the safetensors transfer path (x/transfer), logging
      (slog) and every HTTP handler were not ported.
    - Nullable annotations and Go error wrapping became this library's
      exception types (ModelManagerException and subclasses); Go's byte-based
      string validation became char-based with identical results for the
      ASCII-only grammar.

MODIFICATIONS MADE DURING THE ModelRunner PORT
    - Go's reflection-driven value model became an explicit one - GoValue,
      GoStruct, GoSlice, GoMap and a binder that shapes a chat request into
      it - so the data an Ollama template sees is built by hand here rather
      than discovered by reflection.
    - OllamaTemplateValues carries a System property that Ollama's Values
      struct does not have; it is rendered as a system message prepended to
      the collated messages. Collating copies the message list rather than
      mutating the caller's.
    - Ollama's template.Named became OllamaTemplate.NamedBuiltIn, with the
      same Levenshtein distance (entry 6) and the same threshold of 100.
    - ThinkingParser.Flush returns whatever text is still held back, as
      content; Ollama's parser drops it at end of stream.
    - ToolCallParser clears its buffer on the early return that decides a bare
      JSON document is content, so nothing can be emitted twice; it searches
      for a call's arguments in document order rather than Go map order, so
      the result is deterministic; it preserves property order in
      ArgumentsJson; it caps how much text it will hold and emits the excess
      as content; and it leaves ToolCall.Id unset, because assigning call ids
      is the chat layer's business in this library, not the parser's.
    - ToolCallFormat and ThinkingTags each gained a route Ollama has no need
      of - inference from a Jinja template's text, and for ToolCallFormat also
      from an already-rendered tool call - because this library renders Jinja
      chat templates beside Go ones. For a DeepSeek-style template that spells
      its tool call across two literals, those two routes can disagree.
    - Ollama's server plumbing around these packages - the scheduler, the HTTP
      handlers, slog logging and the renderer/parser registry - was not
      ported.

WHAT WAS INCORPORATED
    NOTHING. CodeBrix.Ollama.ModelRunner contains an original implementation
    of the Jinja template language, written against the Jinja project's
    published documentation and against the fixture templates in entries 8 to
    14; no Jinja source code was copied. The fifty files under
    src/CodeBrix.Ollama.ModelRunner/Templates/Jinja/ carry no provenance
    marker, and that absence is deliberate and correct.

    Jinja is here because a model's chat_template is written in it, so a
    library that renders chat templates must speak the language. The
    behavioural semantics it had to match - what a filter does, how
    whitespace control works, what a string or list or dict method returns -
    come from Jinja's own documentation and from CPython's documented str,
    list and dict behaviour. The Jinja project is named and its licence is
    reproduced so that the debt is on the record, not because the licence
    compels it.

DELIBERATE DIFFERENCES FROM JINJA
    - `x in undefined` evaluates to false rather than raising; the IBM Granite
      chat template in entry 13 needs that.
    - Tuples are modelled as lists, so items() prints [['k', v]] where Jinja
      prints [('k', v)].
    - A `set` inside a loop is scoped to the iteration, which is Jinja's own
      documented behaviour; namespace() carries a value out of a loop, as in
      Jinja.
    - Runaway macro recursion, runaway nesting and an out-of-range \U escape
      raise ChatTemplateException instead of exhausting memory or producing an
      invalid character.

MODIFICATIONS MADE DURING THE PORT

      array operations became loops, and the tools' own file handling was

      library asks those tools for. The other operators upstream's integer
      registry covers are not ported, and are refused if they are asked for.

      none, and requires a model that records having been through it.
    - The tools' warnings, logging and command-line entry points were not
      ported.

      half-precision and bfloat16 paths, its quantized key-value cache, its
      flash-attention and MLAS micro-kernels, its prepacking and its thread-pool
      cost models are not ported; the managed engine spreads its own work and
      refuses by name every attribute and optional input that would take it down
      one of those paths.
    - MatMulNBits' accuracy_level is read and IGNORED. It asks a runtime to
      quantize the activations as well, and this engine keeps them in 32-bit
      floats, which is more accurate than anything the attribute permits.
    - GroupQueryAttention is ported for the fp32, non-shared-buffer,
      non-windowed case. Sharing one buffer between past and present, a local
      window, a softcap, a smooth softmax and a quantized cache are refused.

WHAT WAS TAKEN
    LOGIC, by hand, into C#. Nothing from the project is vendored, downloaded,
    executed or referenced as a package, and none of its files is in this
    repository. What was taken is what a MIDI model of that family MEANS - the
    order its two networks are stepped in, which tokens it may answer with at
    each position of an event, and how an event becomes a row of tokens and a
    row of tokens becomes music - so that CodeBrix.Ollama.ModelRunner's
    MidiGenerationModel writes the same music the publisher's own Python
    writes, event for event, with nothing installed.

    Those rules are not written down anywhere but in that code. A vocabulary is
    a numbered list whose order is the order the tokens were handed out; a
    sampling mask is a list of which numbers are allowed where; and the
    tidying-up a piece goes through on its way in - channels and tracks
    re-numbered into the order they are used, an instrument given to a channel
    that chose none, everything before the first note gathered into a setup -
    is what the model was trained to see. Guess at any one of them and the
    model still runs and still writes rows of tokens; it just writes different
    music.

MODIFICATIONS MADE DURING THE PORT
    - Python became C#: dictionaries whose ORDER the algorithm depends on
      became collections that keep an order of their own, numpy array
      operations became loops, and the loop's io_binding became this
      repository's own tensor interface.
    - ONE PIECE AT A TIME. Upstream writes several pieces side by side in one
      batch; this driver writes one, so every branch that exists to keep
      several in step is gone, and the one place where the batch changes the
      answer - the row length a batch settles on when its pieces have finished
      at different lengths - is ported as the single-piece case with the other
      branch kept and marked.
    - The random numbers are NOT the publisher's. Upstream draws from numpy's
      generator; this library has one of its own, written out so that a seed
      means one thing for ever. Only GREEDY generation - the most likely answer
      every time, and no number drawn at all - is claimed to be identical, and
      that is what is proved against the publisher's Python on the published
      model.
    - A piece to CONTINUE has the tokenizer's end-of-piece row taken off it
      before the model sees it. Upstream leaves it on when a caller asks for
      more events than the piece has, which shows the model "and that is the
      end" and then asks for more.
    - The tokenizer's version one is not ported. The published model this
      driver was written for asks for version two, says so in its own
      configuration, and a bundle asking for another version is refused by
      name.
    - midi2img, augment and check_quality are not ported: the first draws a
      picture, and the other two belong to training rather than to generating.
    - The events this library hands out carry an ABSOLUTE position in ticks, a
      note's length in ticks, and a horizon - none of which upstream computes,
      because upstream hands its events to a web page rather than to a player.

    ModelRunner's managed tokenizer ports, so that turning text into token
    numbers needs nothing installed)

Project:        https://github.com/huggingface/transformers
Licence:        Apache License 2.0
Copyright:      Copyright 2018 The OpenAI Team Authors and The HuggingFace Inc.
                team. Copyright (c) 2018, NVIDIA CORPORATION.
Version read:   v4.57.6, the version installed in the maintainer's virtual
                environment and read there
File read:      src/transformers/models/gpt2/tokenization_gpt2.py

WHAT THIS IS, AND WHY IT IS NOT A MODEL'S FILE. Every bundle of the family this
driver reads carries a COPY of that one file, renamed and with different default
token names, because the publishers ship their tokenizer as remote code. The
copies are byte-identical to the transformers file in everything that matters -
the byte-to-symbol table, the pre-tokenizer pattern, the merge loop, the
encoding and the decoding - which was checked by diffing one against the
installed library. So the upstream recorded here is transformers itself rather
than any one publisher's copy of it, which is both the true source and the one
that does not tie this library to a model.

SCOPE - the file-to-file list, which is what the marker greps must match:

    src/transformers/models/gpt2/tokenization_gpt2.py@v4.57.6
        -> src/CodeBrix.Ollama.ModelRunner/Tokenizers/Gpt2ByteTable.cs
           bytes_to_unicode(): the 256-symbol table and the order the
           unprintable bytes are allotted their symbols in
        -> src/CodeBrix.Ollama.ModelRunner/Tokenizers/Gpt2PreTokenizer.cs
           the pre-tokenizer pattern's RULE - see the modification below
        -> src/CodeBrix.Ollama.ModelRunner/Tokenizers/Gpt2ByteLevelTokenizer.cs
           bpe(), get_pairs(), _tokenize(), _convert_token_to_id(),
           _convert_id_to_token() and convert_tokens_to_string(), together with
           the added-token splitting PreTrainedTokenizer.tokenize() does and the
           grouping PreTrainedTokenizer._decode() does around it

    The two files beside them - Gpt2TokenizerSettings.cs and Gpt2AddedToken.cs -
    and the reader Gpt2TokenizerFiles.cs carry NO marker: they are this
    repository's own way of holding what a bundle's configuration files say, and
    the refusals in the reader are its own.

MODIFICATIONS, and there are four worth stating:

  * THE PRE-TOKENIZER IS A SCAN, NOT A REGULAR EXPRESSION. The Python runs one
    pattern on an engine that works in CODE POINTS; .NET's regular-expression
    engine works in UTF-16 units, where a character outside the basic
    multilingual plane is a surrogate pair and no letter or number class matches
    either half of it. The scan implements the pattern's alternatives in the
    order the pattern writes them and reads one code point at a time, so it
    agrees with the Python everywhere rather than only inside the basic plane.
    The test suite holds it to a compiled .NET regular expression of exactly
    that pattern over the basic plane, and to the framework's own character
    classes over all 65,536 of those characters.
  * THE MERGE FILE IS READ BY THIS REPOSITORY'S OWN RULE, in
    CodeBrix.Ollama.Core (entry 1): a first line is dropped only when it begins
    with `#`, where the Python drops the first line whatever it is. On the
    bundles this driver reads the two select the same table, because a bundle
    written by a model builder carries the header the Python's own save path
    writes; MAINTAINER-README states the case where they would differ.
  * THE CACHE IS A MERGED PIECE'S TOKEN NUMBERS rather than its merged symbol
    string, which is the same answer computed once instead of twice.
  * NOTHING ELSE OF PreTrainedTokenizer IS PORTED: no padding, no truncation, no
    attention masks, no chat template, no fast-tokenizer conversion and no
    saving. A bundle asking for an added token with lstrip, rstrip or
    single_word set is refused by the name of the rule rather than tokenized a
    different way from the way it was trained.

WHAT IS NOT FROM transformers: everything else under Tokenizers/ and everything
under Drivers/CausalLm/, which is this repository's own.
